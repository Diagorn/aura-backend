# AGENTS.md — aura-backend

Guidance for AI agents working on **Aura** — an emotion-tracking backend with two clients (web frontend, Telegram bot).

## Project overview

- **Modular monolith** (`apps/rest-api`) assembled from domain modules. The Telegram bot is a **separate application in its own repository** that talks to the core over REST only (no DB of its own) — see [docs/telegram-bot.md](docs/telegram-bot.md).
- Stack: Spring Boot 4.x, Spring Framework 7, Kotlin 2.x, JDK 21, Gradle multi-module (Kotlin DSL), PostgreSQL + Redis, **Liquibase** (not Flyway), OpenAPI **spec-first**, JWT, detekt.

## Repo layout

- `api/openapi/` — OpenAPI spec; **source of truth** for server, frontend, and bot
- `modules/` — domain modules: `shared`, `auth`, `user`, `catalog`, `entry`, `note`, `analytics`, `notification`
- `apps/rest-api/` — the single deployable of this repository (the web frontend and the Telegram bot live in separate repos and consume the published OpenAPI spec)
- `build-logic/` — convention plugins (`aura.*`); `gradle/libs.versions.toml` — the **only** place for dependency versions
- `aura-api.postman_collection.json` — Postman collection with runnable requests for every endpoint; must be updated when endpoints change (see hard rule 8)

## Hard rules (project-specific)

1. **Spec-first**: contract changes start in `api/openapi/api.yaml` → regenerate (`./gradlew generateApi`) → implement generated interfaces. Never hand-write DTOs that exist in the spec. Generated code lives in `build/` and is never committed.
2. **Module boundaries**: a module exposes only its `….<module>.api` package; cross-module interaction via public interfaces and application events (Spring Modulith). No SQL joins and no FKs across module schemas — references by id only. Verified by Modulith verification + ArchUnit tests.
3. **Migrations are Liquibase**: per-module changelogs in `modules/<m>/src/main/resources/db/changelog/<m>/`, included by `apps/rest-api`'s `master.yaml`. Never edit an applied changeset; id format `<module>-<NNN>-<slug>`; seed data under `context: seed`. The `flyway-migrations` skill does **not** apply to this repo.
4. **DB conventions**: `timestamptz` in UTC; `entries.entry_date` is the user's local date derived from `users.timezone`; enums as `SCREAMING_SNAKE_CASE`; ids `bigint generated by default as identity`; snake_case in DB vs camelCase in DTOs.
5. **API conventions**: `/api/v1` path versioning, additive changes only within v1; errors are RFC 9457 `application/problem+json` with `code`/`errors` extensions; pagination `page`/`size` (max 100) with `{items, page, size, totalElements, totalPages}` envelope; analytics periods accept `from`+`to` or `period=week|month|half_year|year`.
6. **Security**: user JWT — access 15 min + refresh with rotation/reuse detection; the bot authenticates with a service JWT (`typ=service`) for `/internal/v1/**` and acts on behalf of users via token exchange. `/internal/**` is never public.
7. **Customizable domain**: emotions, factors, events, tracked metrics, and note templates follow the "system (`owner_user_id IS NULL`) + personal" pattern. System (seed) entries are modified only by ADMIN; regular users cannot edit them — they personalize by creating their own entries and hiding system ones per-user. Mood/energy/etc. are metrics, not columns.
8. **Postman collection is kept in sync**: whenever an endpoint is added, changed, or removed, update `aura-api.postman_collection.json` (repo root) in the same change — new request with examples (success + RFC 9457 errors) and token-saving test scripts where applicable.
9. **Module docs are kept in sync**: any change to a module's contract, schema, or behavior updates its `docs/modules/<module>.md` (create the file if missing) and affected `docs/` pages (`domain-model.md`, `api-design.md`, …) in the same change. Docs are part of the definition of done, not an afterthought.

## Stack

- Spring Boot 4.x, Spring Framework 7, Kotlin 2.x, JDK 21
- Gradle wrapper: `./gradlew`, Kotlin DSL (`build.gradle.kts`, `settings.gradle.kts`)
- Jakarta EE 11, Jackson 3, and Boot 4 modular starters
- Use dedicated technology test starters rather than the classic test starter
- Keep `kotlin("plugin.spring")` (all-open) applied so `@Configuration`, `@Transactional`, and proxied beans are not final; open JPA entities with `kotlin("plugin.jpa")` (wired via `aura.kotlin-spring` convention plugin)

## Commands

- Build: `./gradlew build` (tests + detekt)
- Tests: `./gradlew test`; single module/class: `./gradlew test --tests "com.aura…"` (integration tests use Testcontainers → Docker must be running)
- Static analysis: `./gradlew detekt`; coverage: `./gradlew koverHtmlReport`
- Run API: `./gradlew :apps:rest-api:bootRun` (Swagger UI at `http://localhost:8080/swagger-ui.html`, profile `local`). The Telegram bot runs from its own repository (see [docs/telegram-bot.md](docs/telegram-bot.md)).
- Regenerate API code: `./gradlew generateApi`
- Infrastructure only: `docker compose up -d` (Postgres :5432, Redis :6379) — see [docs/local-dev.md](docs/local-dev.md)

## Engineering Rules

- Inspect neighboring code and the dependency tree before choosing an API or starter.
- Keep controllers as adapters and transactions in application services.
- Entity lookups with failure live in repositories: `findById(...).orElseThrow(...)` and "fetch owned or 404" belong in repository methods (`require*`), services only orchestrate on the returned entity.
- Be explicit about writes: call `save()` when an entity's state changes (`create` and `update`), even though Hibernate dirty checking would flush it — the write point should be visible in code.
- Use DTOs; do not expose JPA entities as external contracts.
- Use `tools.jackson` APIs for Jackson customization.
- Use **MockK** for test doubles: plain `mockk` in unit tests, `@MockkBean` (springmockk) in slice tests. Explicit test auto-configuration. Skill `testing-pyramid` examples use Mockito — translate them to MockK idioms.
- Preserve error, security, pagination, nullability, and observability contracts.
- Model optionality with Kotlin nullable types; avoid platform types at API and persistence boundaries.
- **Never use the Kotlin `!!` operator** in production code (`src/main`, build logic): a bare `!!` throws a context-free `NullPointerException`. Replace it with an explicit null check that fails with a meaningful error — `checkNotNull(x) { "…" }` / `requireNotNull(x) { "…" }` for invariants, `error("…")` for unreachable states, or the module's `ApiException` (e.g. `ValidationFailedException`) when the null comes from user input. Tests may use `!!` sparingly.

## Verification

Run focused tests and then `./gradlew build` (includes detekt). When touching module boundaries, also run the Modulith verification and ArchUnit tests in `apps/rest-api`. Report any verification that could not run.

## Git — MANDATORY

- **At the end of every work session, stage EVERYTHING you created or changed (`git add -A`)** — including docs and configs. Never leave new or changed files unstaged: the working tree must contain no untracked/modified paths.
- **Do NOT commit.** The user reviews staged changes and commits themselves.
- Do not push unless the user explicitly asks.
